## 2. 算法一：多重归一化（PayloadNormalizer）

### 2.1 设计动机

攻击者常用编码手段隐藏 payload。若不做归一化，任何检测都可被简单编码绕过。

| 混淆手法 | 示例 | 归一化后 |
|---|---|---|
| URL 单重编码 | `%27%20OR%201%3D1` | `' OR 1=1` |
| URL 双重编码 | `%2527%2520OR` | `' OR` |
| HTML 实体 | `&#39; OR 1=1` | `' OR 1=1` |
| Unicode 转义 | `\u0027 OR 1=1` | `' OR 1=1` |
| 全角字符 | `′ ＯＲ １＝１` | `' OR 1=1` |
| 内联注释 | `/*!50000UNION*/` | `UNION` |
| 多余空白 | `OR\t\n\r 1=1` | `OR 1=1` |
| 大小写混淆 | `oR uNiOn` | `or union` |

### 2.2 算法伪码

```
FUNCTION normalize(raw):
    s ← raw
    depth ← 0
    // 循环解码直到不动点，防御多重编码
    WHILE depth < MAX_DEPTH(=5):
        prev ← s
        s ← urlDecode(s)
        s ← htmlEntityDecode(s)
        s ← unicodeUnescape(s)
        IF s == prev: BREAK
        depth ← depth + 1
    
    IF depth >= MAX_DEPTH:
        markSuspicious("EXCESSIVE_ENCODING")   // 过度编码本身即高风险信号
    
    s ← unicodeNFKC(s)          // 全角→半角，兼容等价规范化
    s ← stripInlineComments(s)   // /*!...*/ → 内容; /*...*/ → 空格
    s ← collapseWhitespace(s)    // 连续空白 → 单空格
    s ← removeNullBytes(s)       // %00 截断
    RETURN NormalizeResult(s, s.toLowerCase(), depth, flags)
```

### 2.3 关键边界

- **解码深度上限 5 层**：防止解码炸弹导致 CPU 耗尽（可用性防护）
- **过度编码即信号**：`depth ≥ 3` 直接加 20 风险分——正常业务不会三重编码
- **注释处理区分 MySQL 内联注释**：`/*!50000SELECT*/` 在 MySQL 中会被**执行**，因此必须保留内容而非整体删除，否则会漏报

## 3. 算法二：SQL AST 字面量归一化 ★ 核心创新

### 3.1 核心思想

一条 SQL 的**语义结构**由其语法树的形状决定，而与其中的具体常量值无关。

```sql
SELECT * FROM notes WHERE id = 42       -- 结构 A
SELECT * FROM notes WHERE id = 1337     -- 结构 A（相同！仅常量不同）
SELECT * FROM notes WHERE id = 42 OR 1=1 -- 结构 B（不同！多了 OR 子树）
```

因此：**把所有字面量替换为统一占位符后，正常业务的同一接口必然收敛为极少数几个固定结构**。任何注入都会引入新的结构。

### 3.2 归一化规则表

| AST 节点类型 | 归一化动作 | 示例 |
|---|---|---|
| 字符串字面量 | → `?` | `'alice'` → `?` |
| 数值字面量 | → `?` | `42` → `?` |
| 日期/时间字面量 | → `?` | `'2026-01-01'` → `?` |
| 布尔字面量 | → `?` | `TRUE` → `?` |
| NULL | **保留** | `NULL`（语义相关，不可归一） |
| 表名 / 列名 | **保留原样** | `notes.title`（结构的一部分） |
| 函数名 | **保留** | `SLEEP`、`CONCAT`（关键风险信号） |
| 运算符 | **保留** | `=`、`AND`、`OR`、`UNION` |
| IN 列表 | → 单个 `?`（长度无关化） | `IN (1,2,3)` → `IN (?)` |
| LIMIT 值 | → `?` | `LIMIT 10` → `LIMIT ?` |
| 别名 | 保留 | `AS t1` |

> **为什么 IN 列表要长度无关化**：`IN (1,2)` 与 `IN (1,2,3)` 是同一业务语义，若不归一会产生基线爆炸（每种长度一个指纹）。这是工程实践中的关键细节。

> **为什么函数名必须保留**：`SLEEP(5)`、`BENCHMARK()`、`LOAD_FILE()`、`EXTRACTVALUE()` 是时间盲注与带外注入的标志。若把函数也归一化就会漏报最危险的一类攻击。

### 3.3 实现方式（JSqlParser 访问者模式）

```java
/**
 * [SEC-SQLI-02] AST 字面量归一化
 * 
 * 安全原理：
 *   遍历语法树，将所有字面量常量替换为占位符 '?'，保留表名、列名、
 *   函数名、运算符等决定语义结构的节点。归一化后的语句仅反映 SQL
 *   的"骨架形状"，与具体参数取值无关。
 *   
 *   这是结构指纹能够抵御编码混淆的根本原因：攻击者可以任意改变
 *   参数的文本形态，但只要他想改变查询逻辑（这正是注入的目的），
 *   就必须引入新的语法节点，骨架必然改变。
 * 
 * 威胁对应：T-01 (Tampering, DREAD 9.0)
 */
public class AstNormalizer extends ExpressionVisitorAdapter {

    @Override
    public void visit(StringValue value) {
        replaceWithPlaceholder(value);   // 'alice' → ?
    }

    @Override
    public void visit(LongValue value) {
        replaceWithPlaceholder(value);   // 42 → ?
    }

    @Override
    public void visit(InExpression expr) {
        // [关键] IN 列表长度无关化，避免基线因参数个数不同而爆炸
        collapseItemsList(expr);         // IN (1,2,3) → IN (?)
    }

    @Override
    public void visit(Function function) {
        // [关键] 函数名必须保留：SLEEP / BENCHMARK / LOAD_FILE
        // 是时间盲注与带外注入的核心标志，归一化会导致严重漏报
        keepName(function);
        visitArguments(function);        // 仅归一化参数
    }
    // ...
}
```

### 3.4 完整示例

```
输入 SQL:
  SELECT id,title FROM notes WHERE owner='alice' AND id=42 LIMIT 10

归一化:
  SELECT id, title FROM notes WHERE owner = ? AND id = ? LIMIT ?

指纹:
  SHA-256 → a3f9c2e1...（取前 16 字节 hex）


注入 SQL:
  SELECT id,title FROM notes WHERE owner='alice' AND id=42 OR 1=1 -- '

归一化:
  SELECT id, title FROM notes WHERE owner = ? AND id = ? OR ? = ?
                                                        ^^^^^^^^^^ 新增结构

指纹:
  SHA-256 → 7b1d40aa...   ← 与基线失配 → 判定为注入
```

## 4. 算法三：规范化序列化与指纹计算

### 4.1 为什么不能直接对 SQL 文本做哈希

同一语义的 SQL 存在多种等价书写：大小写不同、空白不同、可选关键字（`AS`、`INNER`）省略与否、括号冗余等。直接哈希文本会导致同一结构产生多个指纹。

### 4.2 规范化序列化规则

对归一化后的 AST 做**深度优先遍历**，按固定规则输出规范形式：

1. 所有关键字统一大写：`select` → `SELECT`
2. 所有标识符统一小写：`Notes` → `notes`
3. 单空格分隔，去除所有冗余空白
4. 补全可选关键字：`INNER JOIN` 显式化，别名补 `AS`
5. 去除语义冗余括号，保留影响优先级的括号
6. `AND`/`OR` 的**同级操作数排序无关化**（可选增强）：对交换律成立的同级布尔操作数按序列化文本排序后再连接，使 `a=? AND b=?` 与 `b=? AND a=?` 收敛为同一指纹

```
FUNCTION fingerprint(sql, endpoint):
    ast        ← parse(sql)                    // JSqlParser
    normAst    ← AstNormalizer.apply(ast)      // 字面量归一化
    canonical  ← AstSerializer.serialize(normAst)  // 规范化序列化
    // 指纹绑定 endpoint，避免跨接口误命中
    RETURN SHA256(endpoint + "|" + canonical)[0:32]
```

### 4.3 指纹绑定 endpoint 的理由

若指纹全局共享，接口 A 的合法结构可能被攻击者用于接口 B 从而绕过。指纹 = `Hash(endpoint + canonical)` 保证**基线是接口级隔离**的。

## 5. 算法四：AST 结构差分定位 ★ 可视化数据源

### 5.1 目标

指纹失配只能回答"变了没有"，无法回答"变在哪"。结构差分要输出**具体是哪个节点被注入**，这既是取证依据，也是大屏红色高亮子树的数据来源。

### 5.2 算法：基于路径签名的树差分

不使用完整的树编辑距离（Zhang-Shasha，O(n²·…) 过重），采用**节点路径签名集合差**，复杂度 O(n)：

```
FUNCTION diff(baselineAst, actualAst):
    // 1. 为每个节点生成路径签名：从根到该节点的类型路径 + 节点自身特征
    //    例："SELECT/WHERE/AndExpr[0]/EqualsTo"
    baseSigs ← collectPathSignatures(baselineAst)   // Multiset
    actSigs  ← collectPathSignatures(actualAst)

    added   ← actSigs  - baseSigs     // 多集差：新增节点
    removed ← baseSigs - actSigs      // 缺失节点

    // 2. 对新增节点做语义标注
    annotations ← []
    FOR node IN added:
        kind ← classify(node)
        annotations.add({
            path:     node.path,
            nodeType: node.type,
            snippet:  node.toString(),
            kind:     kind,          // OR_INJECTION / UNION / STACKED / COMMENT / FUNC_CALL
            severity: severityOf(kind)
        })

    // 3. 计算结构相似度（用于风险分）
    similarity ← |baseSigs ∩ actSigs| / |baseSigs ∪ actSigs|   // Jaccard

    RETURN DiffResult(added, removed, annotations, similarity)
```

### 5.3 新增节点的语义分类表

| 分类 | 判定条件 | 严重度 | 含义 |
|---|---|---|---|
| `TAUTOLOGY` | 新增比较表达式两侧归一化后恒等（`?=?`） | CRITICAL | 恒真式绕过 |
| `OR_INJECTION` | WHERE 子树新增 `OrExpression` | CRITICAL | 逻辑绕过 |
| `UNION_INJECTION` | 新增 `SetOperationList`(UNION) | CRITICAL | 联合查询脱库 |
| `STACKED_QUERY` | 解析出多条 Statement | CRITICAL | 堆叠查询 |
| `COMMENT_TRUNCATION` | 尾部注释截断原结构（`removed` 非空且原尾部丢失） | HIGH | 注释闭合 |
| `DANGEROUS_FUNC` | 新增函数 ∈ {SLEEP, BENCHMARK, LOAD_FILE, EXTRACTVALUE, UPDATEXML, ...} | CRITICAL | 盲注/带外 |
| `SUBQUERY_INJECTION` | 新增子查询节点 | HIGH | 嵌套查询注入 |
| `COLUMN_EXPANSION` | SELECT 列数增加 | MEDIUM | 信息扩展 |
| `CONDITION_REMOVED` | `removed` 中含 WHERE 条件 | HIGH | 条件被剥离（全表泄露） |

## 6. 算法五：风险特征启发式检测（冷启动兜底）

### 6.1 设计动机

基线学习需要时间。系统刚部署或遇到新接口时基线为空，此时若"一律拦截"会阻断正常业务，若"一律放行"则形同虚设。因此需要一套**不依赖基线**的判定规则。

**注意**：这里的"特征"作用于**已解析的 AST 结构**，而非原始文本正则——这与传统 WAF 有本质区别。

### 6.2 风险特征表

| 编号 | 特征 | 检测方式（AST 层） | 分值 |
|---|---|---|---|
| R-01 | 恒真式 | 比较表达式两侧归一化后结构相同且运算符为 `=`，或字面量自比较 | 40 |
| R-02 | UNION 查询 | AST 根为 `SetOperationList` 且操作符含 UNION | 45 |
| R-03 | 堆叠查询 | `parseStatements` 返回 > 1 条语句 | 50 |
| R-04 | 注释截断 | 词法层检测尾部 `--` / `#` / `/*` 且其后原结构缺失 | 35 |
| R-05 | 时间盲注函数 | 函数名 ∈ {SLEEP, BENCHMARK, WAITFOR, PG_SLEEP} | 50 |
| R-06 | 带外/文件函数 | 函数名 ∈ {LOAD_FILE, INTO OUTFILE, EXTRACTVALUE, UPDATEXML} | 50 |
| R-07 | 系统表访问 | 表名 ∈ {information_schema.*, mysql.user, pg_catalog.*} | 45 |
| R-08 | 布尔盲注模式 | WHERE 中出现 `AND (SELECT ...)` 子查询比较 | 35 |
| R-09 | 十六进制/CHAR 编码绕过 | 出现 `0x…` 长串或 `CHAR(…)` 拼接 | 25 |
| R-10 | 过度编码 | 归一化解码深度 ≥ 3 | 20 |
| R-11 | 逻辑运算符异常增多 | OR/AND 数量显著超出该接口历史均值 | 20 |
| R-12 | 版本探测函数 | `@@version` / `VERSION()` / `DATABASE()` | 30 |

### 6.3 综合风险评分

```
FUNCTION riskScore(diffResult, features, normalizeMeta):
    score ← 0

    // 结构差分贡献（有基线时）
    IF hasBaseline:
        score += (1 - similarity) × 50
        FOR ann IN annotations:
            score += weightOf(ann.severity)   // CRITICAL 40 / HIGH 25 / MEDIUM 10

    // 风险特征贡献（始终生效）
    FOR f IN features:
        score += f.weight

    // 编码可疑度
    score += normalizeMeta.depth × 5

    RETURN min(score, 100)


判定阈值：
    score ≥ 70  → CRITICAL，BLOCK 模式下拦截
    50 ≤ s < 70 → HIGH，记录并告警
    30 ≤ s < 50 → MEDIUM，记录
    s < 30      → 放行
```

### 6.4 降低误报的工程手段

1. **基线优先**：指纹命中基线则直接 PASS，不再计算风险分（避免正常业务被特征误伤）
2. **接口级白名单**：允许管理员对特定接口/参数设置豁免
3. **学习期观察**：新接口首次出现时先记录不拦截，累计 N 次后转入防护
4. **相似度容差**：Jaccard 相似度 > 0.95 且无 CRITICAL 标注时视为等价结构

## 7. 算法六：XSS 语义净化（无正则）

### 7.1 设计动机

正则过滤 XSS 是经典反面教材。`<script>` 被过滤可以用 `<img onerror>`、`<svg onload>`、`<iframe srcdoc>`、`javascript:` 伪协议、HTML 实体编码、大小写混淆、标签属性换行分隔等无数手法绕过。

正确做法是：**把 HTML 当作 HTML 解析**，构建 DOM 树，然后基于白名单判定每个节点是否允许存在。

### 7.2 三级白名单模型

```
一级：标签白名单
  允许 { p, br, strong, em, u, h1-h6, ul, ol, li, blockquote,
         code, pre, a, img, table, thead, tbody, tr, td, th, span, div }
  其余标签一律移除（含 script / iframe / object / embed / svg / math / form / style / link / meta）

二级：属性白名单（按标签细分）
  a   → { href, title, target }
  img → { src, alt, width, height }
  td  → { colspan, rowspan }
  通用 → { class }（且 class 值须匹配允许的样式前缀）
  ★ 所有 on* 事件属性一律禁止（onerror/onload/onclick/onmouseover/...）
  ★ style 属性禁止（可用于 expression()、url(javascript:) 等）

三级：协议白名单
  href/src 的协议 ∈ { http, https, mailto, 相对路径 }
  ★ 禁止 javascript:、data:、vbscript:、file:
  ★ 判定前必须先做多重解码 + 去除空白/控制字符
     （防御 "java\tscript:" 、"java&#115;cript:" 等绕过）
```

### 7.3 实现要点

```java
/**
 * [SEC-XSS-01] 基于 DOM 解析的 HTML 语义净化
 * 
 * 安全原理：
 *   不使用正则匹配危险标签（该做法可被 <svg/onload>、伪协议、
 *   实体编码等手法绕过）。本实现将输入按 HTML 规范解析为 DOM 树，
 *   逐节点依据"标签→属性→协议"三级白名单裁决，凡不在白名单内
 *   的元素、属性、协议一律移除。
 *   
 *   白名单机制保证：即使出现未知的新型绕过手法，只要它依赖于
 *   白名单之外的标签或属性，就自动失效。
 * 
 * 威胁对应：T-02 (Tampering/XSS, DREAD 8.0)
 */
public class HtmlSanitizer {

    public SanitizeResult sanitize(String input) {
        // 1. 解码归一化（防御实体编码绕过）
        String decoded = normalizer.normalize(input).value();

        // 2. DOM 解析
        Document doc = Jsoup.parseBodyFragment(decoded);

        // 3. 遍历裁决，记录被移除的内容作为攻击证据
        List<Removal> removals = new ArrayList<>();
        traverseAndFilter(doc.body(), removals);

        // 4. 输出转义（禁止保留原始 HTML 实体歧义）
        doc.outputSettings().escapeMode(Entities.EscapeMode.base);

        return new SanitizeResult(doc.body().html(), removals);
    }

    private boolean isSafeUrl(String url) {
        // [关键] 先剥离空白与控制字符，再判协议
        // 防御 "java\tscript:alert(1)" / "  javascript:..." 类绕过
        String u = url.replaceAll("[\\s\\p{Cntrl}]", "").toLowerCase();
        u = normalizer.normalize(u).value();
        if (u.startsWith("javascript:") || u.startsWith("data:")
            || u.startsWith("vbscript:") || u.startsWith("file:")) {
            return false;
        }
        return true;
    }
}
```

### 7.4 必须通过的绕过测试集

| # | Payload | 预期结果 |
|---|---|---|
| 1 | `<script>alert(1)</script>` | 标签移除 |
| 2 | `<img src=x onerror=alert(1)>` | `onerror` 属性移除 |
| 3 | `<svg/onload=alert(1)>` | 标签移除 |
| 4 | `<a href="javascript:alert(1)">x</a>` | href 置空 |
| 5 | `<a href="java&#115;cript:alert(1)">x</a>` | 解码后识别，置空 |
| 6 | `<a href="  java\tscript:alert(1)">x</a>` | 去空白后识别，置空 |
| 7 | `<IMG SRC=x ONERROR=alert(1)>` | 大小写无关，属性移除 |
| 8 | `<iframe srcdoc="<script>alert(1)</script>">` | 标签移除 |
| 9 | `<body onload=alert(1)>` | 标签+属性移除 |
| 10 | `<div style="background:url(javascript:alert(1))">` | style 属性移除 |
| 11 | `<math><mtext><script>alert(1)</script>` | 命名空间混淆，标签移除 |
| 12 | `<p>正常<strong>加粗</strong>内容</p>` | **完整保留**（验证不误伤） |

> 第 12 条极其重要：净化器不能"一刀切全删"，必须证明正常富文本可用，否则功能性不达标。

## 8. 算法七：限流与 IP 信誉

### 8.1 双算法组合

**令牌桶**（应对突发）：
```
容量 C = 100，填充速率 r = 20 tokens/s
请求到达时按时间差补充令牌：tokens = min(C, tokens + Δt × r)
若 tokens ≥ 1 则放行并 tokens--，否则拒绝
```

**滑动窗口**（应对持续高频）：
```
窗口 W = 60s，切分为 12 个 5s 的桶
统计最近 W 内请求总数，超过阈值 T（默认 600）则拒绝
环形数组实现，O(1) 更新
```

两者取"与"：任一超限即触发 429。

### 8.2 IP 信誉评分

```
FUNCTION updateReputation(ip, event):
    rep ← get(ip) or new(score=0)
    rep.score += severityWeight(event.severity)   // CRITICAL +30, HIGH +15, MEDIUM +5
    rep.lastSeen ← now()

    // 时间衰减：每小时衰减 10%，避免永久封禁
    rep.score ← rep.score × pow(0.9, hoursSince(rep.lastDecay))

    IF rep.score ≥ 100:
        rep.status ← BLOCKED
        rep.blockUntil ← now() + 30min      // 自动过期，防误封
    
    RETURN rep
```

## 9. 算法八：路径穿越与命令注入检测

### 9.1 路径穿越

```
FUNCTION isPathTraversal(userPath, rootDir):
    decoded ← normalize(userPath)              // 多重解码，处理 %2e%2e%2f
    target  ← Path.of(rootDir, decoded).normalize().toAbsolutePath()
    root    ← Path.of(rootDir).normalize().toAbsolutePath()
    // [关键] 用规范化后的绝对路径做前缀判定，而非字符串黑名单过滤 "../"
    //        黑名单可被 ....// 、%252e%252e 等绕过
    RETURN NOT target.startsWith(root)
```

### 9.2 命令注入（RASP 层）

探针钩住 `ProcessBuilder.start()` 与 `Runtime.exec()`：

```
FUNCTION onCommandExecute(command, args):
    // 1. 单字符串形式的 exec 本身即高危（会经 shell 解析）
    IF isSingleStringForm:
        raiseEvent(CRITICAL, "使用了 shell 解析型命令执行")

    // 2. 检测 shell 元字符
    metaChars ← { ; | & $ ` \n > < ( ) }
    IF anyArgContains(metaChars):
        raiseEvent(CRITICAL, "命令参数含 shell 元字符")

    // 3. 与该调用点的历史基线比对（同 SQL 基线思想）
    IF commandNotInBaseline(callSite, command):
        raiseEvent(HIGH, "调用点执行了非基线命令")
```

## 11. 算法局限性与改进方向（报告加分项）

诚实讨论局限性能显著提升报告的学术性，也是答辩中的加分回答：

1. **依赖 SQL 可解析性**：JSqlParser 对某些数据库方言支持有限，遇到解析失败需降级。改进方向：接入 ANTLR 自定义语法或多解析器投票。
2. **基线依赖学习质量**：若学习期内混入攻击流量，会污染基线。改进方向：学习期人工审核 + 离群点剔除。
3. **动态 SQL 场景**：业务本身若使用高度动态拼接（如可变列的报表查询），会产生大量合法指纹。改进方向：引入结构模板泛化（把可变部分抽象为通配子树）。
4. **二阶注入**：攻击载荷先入库、后续查询时才触发。本系统 RASP 层可检出触发时刻的结构异常，但无法溯源到最初的写入请求。改进方向：数据流污点标记跨请求追踪。
5. **加密流量**：网关层需 TLS 终止才能检测。改进方向：部署为 TLS 终止点或旁路解密。
